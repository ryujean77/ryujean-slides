# 18강. 자동화가 실패할 때 — 기록하고, 되돌리고, 다른 길로

유정근 · 마이웨이 아카데미 | C3 업무 자동화
척추: 12블럭 B12

## 오늘의 목표

내 자동화가 실패하는 모양을 미리 다섯 가지로 나눠 봅니다. 실패마다 **기록할 곳 · 되돌리는 법 · 다른 길** 세 칸을 채운 "실패 대응표" 한 장을 만들고, 다른 사람(또는 다른 AI)에게 일을 넘길 때 쓰는 인계 메모 양식을 만듭니다.

## 먼저 이해하기

오늘 나오는 말을 먼저 풀어 둡니다.

- **무인 실행**: 사람이 자리에 없을 때 AI나 스크립트가 혼자 일하게 한 실행입니다.
- **되돌리기(롤백)**: 바뀐 것을 바뀌기 전 상태로 돌려놓는 일입니다.
- **다른 길(대체 경로)**: 한 방법이 막혔을 때 쓰는 두 번째 방법입니다. 사람이 손으로 하는 절차도 훌륭한 다른 길입니다.
- **인계 메모**: 하던 일을 다른 사람이나 다른 AI에게 넘길 때, 무엇이 끝났고 무엇이 남았는지 적어 주는 짧은 문서입니다.
- **건너뜀**: 실패가 아니라, 정해 둔 규칙에 따라 일부러 하지 않은 것입니다. 예: "이번 주에 이미 보내서 보내지 않음".

자동화는 반드시 실패합니다. 문제는 실패 그 자체가 아니라, 실패가 **조용히** 일어나는 것입니다. 사람이 하던 일은 실패하면 사람이 압니다. 자동화의 실패는 아무도 모르는 채로 며칠씩 이어질 수 있습니다. 그래서 실패 대응은 세 동사로 정리됩니다.

- **기록한다.** 실패는 크게 드러나야 합니다. "성공"은 정말 성공한 뒤에만 적습니다.
- **되돌린다.** 바꾸기 전에 원본을 남기고, 되돌리는 길을 미리 한 번 걸어 봅니다.
- **다른 길로 간다.** 한 경로가 막혔을 때 쓸 대체 경로를 정해 둡니다.

비유하자면 산행의 하산 계획입니다. 노련한 등산가는 정상에 가는 길보다 내려오는 길을 먼저 확인합니다. 몇 시까지 정상에 닿지 못하면 돌아선다는 시각, 날씨가 나빠지면 쓸 우회로, 산에 오른다고 알려 둔 사람. 이것이 각각 정지선(스스로 멈추는 선, 17강), 다른 길, 기록입니다.

## 강사의 시스템에서

강사의 워크스페이스에는 실패 기록이 성공 기록만큼 많습니다. 여기서는 모양이 서로 다른 다섯 가지를 봅니다.

**① 확인 카드 앞에서 멈춘 무인 실행.** 사람이 자리를 비운 사이 AI에게 작업을 맡겼는데, AI가 파일을 쓰기 전 허락을 묻는 확인 카드(일하기 전에 사람의 허락을 받으려고 대화 안에 띄우는 작은 카드)를 띄웠고 그 카드에 답할 사람이 없었습니다. 결과는 아무 파일도 만들어지지 않은 채 끝난 작업이었습니다. C1에서 배운 확인 카드는 사람이 곁에 있을 때는 안전장치지만, 사람이 없을 때는 정지 버튼이 됩니다. 사람 없이 돌릴 일이라면 권한 범위를 미리 좁게 정해 두거나, 사람이 확인할 수 있는 방식으로 좁은 범위부터 시험합니다. 그리고 끝났다는 보고가 아니라 <strong>결과 파일이 실제로 있는지</strong>로 확인합니다.

**② 사용 한도에 걸려 멈춘 작업.** 긴 작업 도중 AI 도구의 사용 한도(정해진 기간에 쓸 수 있는 양의 상한)가 차서 일이 멈췄고, 남은 일을 다른 AI 에이전트에게 넘겨 마쳤습니다. 이때 넘겨받는 쪽이 가장 먼저 묻는 것은 늘 같습니다. 무엇이 끝났고, 무엇이 남았고, 파일은 어디 있고, 무엇을 건드리면 안 되는가. 강사가 앓아누운 주에 세 에이전트가 일을 나눠 맡을 때도 한도에 대비한 인계 절차를 보고서의 한 절로 따로 두었습니다. 인계 메모가 있으면 한도는 사고가 아니라 교대 시간입니다.

**③ 멈췄는데 살아 있던 작업.** 중단 버튼을 눌렀는데, 뒤에서는 작업이 계속 살아 이어지고 있던 일이 있었습니다. 로컬 작업실(17강의 내 컴퓨터용 초안 실행기) 설명서에는 이 차이가 정확히 적혀 있습니다. "다음 작업 일시정지"는 지금 작업을 멈추지 않습니다. "이 작업 취소"는 현재 모델 응답을 받은 뒤에 결과를 버립니다. "서버 종료"는 화면을 띄우는 프로그램을 닫을 뿐, AI 모델 프로그램은 따로 돌고 있어서 진행 중이던 추론(AI가 답을 만들어 내는 계산)이 잠시 남을 수 있습니다. 교훈은 단순합니다. 멈춤 버튼을 누른 뒤에는 <strong>결과 폴더에 새 파일이 더 생기지 않는지</strong>를 확인하고 나서야 멈췄다고 말합니다.

**④ 성공으로 보인 실패.** 5강의 "처리함을 먼저 적어 통화 한 건이 조용히 증발하는 순서"와 9강의 "승인 실패를 성공으로 표시하던 결재 화면"은 같은 점검에서 함께 나온 결함입니다. 둘 다 오류 메시지 하나 없이 틀립니다. <strong>성공 기록은 성공한 뒤에, 실패는 크게.</strong> 이 원칙을 뒤집는 코드는 동작해도 틀린 코드입니다.

**⑤ 멈추지 않고 끝까지 돌린 판단.** 9강에서 본 대리 결재 사고(순번이 당겨져 보류했던 건이 승인된 일)에는 뒷이야기가 있습니다. 에이전트는 잘못을 알아챘을 때 실행을 중간에 끊지 않았습니다. 승인 한 건은 초안 생성 → 파일 이동 → 목록 등록 → 캘린더 등록 순서로 진행되는데, 중간에 끊으면 파일은 옮겨졌는데 목록은 비어 있는 반쪽 상태가 남습니다. 중복 문서 한 건보다 반쪽 상태가 더 비싸다고 보고 끝까지 돌린 뒤, 결재 스레드(휴대폰 메신저에서 결재를 주고받는 대화 줄)에 "롤백"이라고 답하면 작동하는 공식 되돌리기 경로를 보고서에 적었습니다. **되돌리기는 도중에 끊는 것이 아니라, 끝난 뒤 정해진 길로 돌아가는 것입니다.**

11강의 캘린더 사고는 되돌리기의 순서를 그대로 보여 줍니다. 지우기 전에 백업하고, 한 건이 아니라 공통 기능을 고치고, 같은 조건으로 사고를 재현해 가드(위험한 동작을 막아 세우는 장치)가 막는지 확인했습니다.

강사가 가장 경계하는 실패는 따로 있습니다. "됐다고 보고했는데 실제로는 안 된" 경우입니다. 클라우드 에이전트 기록에는 배포(프로그램을 서버에 올려 실제로 돌게 하는 일) 중 실수를 숨기지 않고 적은 이유가 이렇게 남아 있습니다. "이 프로젝트가 '됐다고 보고했는데 안 되는' 패턴으로 이미 한 번 막혔기 때문이다."

## 가상 예시로 직접 해 보기

아래 인물·자료·기관은 학습용 가상 설정입니다. PC의 크롬에서 합니다. 약 50분이 걸립니다.

### 가. 실패 대응표 만들기

1. 윤하람 씨는 12강의 "설문지 → 시트 → 알림"과 16강의 "주간 요약 저장" 자동화를 놓고 실패 대응표를 만듭니다. 크롬에서 `https://sheets.google.com` 을 열고 '빈 스프레드시트'를 눌러 `실패대응표` 시트를 만듭니다.
2. 첫 행에 칸 다섯 개를 적습니다: `실패 모양 / 어떻게 알게 되나 / 기록할 곳 / 되돌리는 법 / 다른 길`.
3. A2부터 아래로 실패 모양 다섯 줄을 적습니다: `권한·인증에서 멈춤`, `한도에서 멈춤`, `멈췄는데 계속 돎`, `성공으로 보인 실패`, `반쯤 하다 멈춤`.

### 나. "어떻게 알게 되나" — 트리거 실패 알림 켜기

4. 앱스 스크립트는 트리거가 실패하면 실패 요약 메일을 보내 줍니다. 트리거가 켜져 있는 동안에는 이 알림의 빈도를 바꿀 수 있고, 알림을 아예 끄려면 트리거를 끄거나 지워야 합니다.
5. 12강의 신청 시트를 열고 '확장 프로그램' → 'Apps Script'로 편집기를 엽니다. 맨 왼쪽 알람 시계 모양 '트리거'를 누릅니다.
6. "양식 제출 시" 트리거 줄에 마우스를 올리고, 오른쪽에 나타나는 연필 모양(트리거 수정)을 누릅니다. 창 맨 아래 '실패 알림 설정'이 '즉시 알림'인지 봅니다. 아니면 '즉시 알림'으로 바꾸고 '저장'을 누릅니다.
   - 이렇게 보이면 됩니다: 트리거 목록으로 돌아오고, 줄은 그대로 하나입니다.
7. `실패대응표` 의 B열(어떻게 알게 되나)에 적습니다. 예) `권한·인증에서 멈춤` 줄: `트리거 실패 알림 메일(즉시)`. `성공으로 보인 실패` 줄: `알림이 오지 않음 — 그래서 실행기록 시트의 '성공' 줄 수와 실제 결과 수를 매주 비교`.

### 다. "기록할 곳" — 실행기록 시트 만들기

8. 편집기의 실행 기록은 개발 중 확인용이라 오래 남지 않는다고 공식 문서가 밝히고 있습니다. 그래서 기록을 시트에 따로 남깁니다. `실패대응표` 시트 맨 아래 왼쪽의 '+'(시트 추가)를 눌러 새 탭을 만들고, 탭을 마우스 오른쪽 단추로 눌러 '이름 바꾸기' → `실행기록` 으로 바꿉니다.
9. 첫 행에 칸 이름을 적습니다: `시각 / 자동화 이름 / 결과 / 이유`.
10. 결과 칸(C2~C200)을 선택하고 '삽입' → '드롭다운'으로 `성공`, `실패`, `건너뜀` 세 값만 고르게 합니다(14강 12~13단계와 같은 방법).
11. C1 칸을 마우스 오른쪽 단추로 누르고 '메모 삽입'을 고른 뒤 `건너뜀은 실패가 아니다(규칙에 따라 일부러 안 한 것)` 라고 적습니다.
12. 이 시트에 자동화가 스스로 한 줄씩 적게 하려면 코드를 고쳐야 합니다. 아래 두 번째 요청문으로 AGY에게 점검부터 맡깁니다. "성공" 줄은 저장·발송이 끝난 다음에만 있어야 합니다.

### 라. "되돌리는 법" — 한 번 실제로 해 보기

13. `실패대응표` 의 D열(되돌리는 법)을 채웁니다. 참고할 사실은 이렇습니다.
    - 구글 문서·시트: 위쪽 메뉴 '파일' → '버전 기록' → '버전 기록 보기'를 누르면 오른쪽에 이전 버전 목록이 나옵니다. 되돌릴 버전을 누르고 위쪽의 '이 버전 복원하기'를 누릅니다.
    - 드라이브에서 지운 파일: 왼쪽 목록의 '휴지통'에 있다가 30일이 지나면 영구 삭제됩니다. 그 안에 파일을 마우스 오른쪽 단추로 누르고 '복원'을 누릅니다.
    - 구글 문서가 아닌 일반 파일(PDF, 사진 등)의 이전 버전: 30일이 지났거나 100개를 넘으면 지워질 수 있습니다. 파일의 점 세 개(더보기)에서 '버전 관리'를 찾아 열고, 남겨야 할 버전은 '영구 보관'을 켭니다.
14. 되돌리기를 **실제로 한 번** 합니다. 16강의 `시험_신청요약` 시트를 열고, B2 칸의 `시험A` 를 `바뀐값` 으로 고칩니다.
15. '파일' → '버전 기록' → '버전 기록 보기'를 누릅니다. 오른쪽 목록에서 방금 고치기 **전** 시각의 버전을 누르고, 위쪽 '이 버전 복원하기' → 확인 창의 '복원'을 누릅니다.
    - 이렇게 보이면 됩니다: B2 칸이 다시 `시험A` 입니다. 한 번도 걸어 보지 않은 하산로는 하산로가 아닙니다.

### 마. "다른 길"과 "반쯤 하다 멈춤"

16. E열(다른 길)에 자동화마다 수동 절차를 세 줄로 씁니다. 예) `요약이 안 오면: ① 신청 시트를 연다 ② 필터로 이번 주만 본다 ③ 과정별 개수를 세어 메모한다`. (필터는 조건에 맞는 줄만 잠시 보여 주는 기능으로, '데이터' → '필터 만들기'에 있습니다.)
17. `반쯤 하다 멈춤` 줄의 D열에는 `도중에 끊지 않는다, 끝난 뒤 되돌린다` 를 적습니다. 작업이 여러 걸음이면, 걸음마다 결과가 어디에 남는지를 같은 칸에 나열합니다. 예) `① 문서 생성 → 시험_요약저장 폴더 ② 알림 메일 → 받은편지함 ③ 실행기록 한 줄 → 실행기록 탭`.

### 바. 인계 메모 양식과 마지막 확인

18. 크롬에서 `https://docs.google.com` 을 열어 '빈 문서'로 `인계메모_양식` 을 만듭니다. 칸 여섯 개를 한 줄씩 적습니다: `목표 / 끝난 것 / 남은 것 / 파일 위치(폴더 이름만) / 건드리면 안 되는 것 / 마지막으로 확인한 결과와 시각`. 사용 한도로 AI를 바꿔야 할 때, 이 양식을 채워 새 대화의 입력칸에 가장 먼저 붙여 넣습니다.
19. `실패대응표` 맨 아래에 "멈췄다고 말하기 전에 확인할 것"을 한 줄 씁니다. 하람 씨의 답: `결과 폴더에 5분 동안 새 파일이 생기지 않는다`.

(화면의 글자는 버전에 따라 조금 다를 수 있습니다.)

## AI에게 건네는 말

두 요청 모두 AGY에게 보냅니다. 12강·16강에서 AGY가 작업 폴더에 만든 `.gs` 파일을 읽게 합니다.

> **어디에 입력하나요:** 바탕화면이나 시작 메뉴에서 'Antigravity'를 눌러 AGY를 엽니다. 작업 폴더가 열려 있는지 먼저 봅니다(C1 3강). 화면 아래쪽의 채팅 입력칸(에이전트에게 말을 거는 칸)을 누르고, 아래 글을 붙여 넣은 뒤 `Enter` 로 보냅니다. AGY가 대화 안에 계획이나 확인 카드를 먼저 보여 주면, 바로 승인하지 말고 무엇을 하겠다는지 읽은 뒤 결정합니다(C1 9강).

보낼 글 (첫 번째 요청):

> 작업 폴더의 `신청알림_v01.gs` 와 `요약가드_v01.gs` 를 읽고, 실패 모양 다섯 가지(권한·인증에서 멈춤 / 한도에서 멈춤 / 멈췄는데 계속 돎 / 성공으로 보인 실패 / 반쯤 하다 멈춤) 각각이 이 자동화에서 어떻게 일어날 수 있는지 한 줄씩 적어 줘. 일어날 수 없는 것은 왜 없는지도 적어 줘. 코드는 고치지 마.

답을 읽는 법: AI가 적은 한 줄씩을 `실패대응표` 의 해당 줄 옆 빈칸(F열)에 옮겨 붙입니다. "일어날 수 없다"는 줄은 이유가 코드의 어느 부분인지 적혀 있는지 봅니다.

보낼 글 (두 번째 요청):

> 같은 두 파일에서 "성공" 기록이나 "처리함" 표시가 실제 저장·발송보다 먼저 실행되는 곳이 있는지 찾아 줘. 그리고 오류가 났을 때 그 사실이 `실행기록` 시트(칸: 시각 / 자동화 이름 / 결과 / 이유)에 '실패'와 이유로 남도록 하려면 무엇을 더해야 하는지 알려 줘. 한도 때문에 건너뛴 경우는 '실패'가 아니라 '건너뜀'으로 남아야 해. 먼저 계획만 보여 주고, 내가 승인하면 파일 이름 끝을 `_v02` 로 바꾼 새 파일로 고쳐 줘. 원래 파일은 그대로 둬.

답을 읽는 법: 계획에 "원래 파일을 덮어쓴다"가 있으면 승인하지 않습니다. `_v02` 파일이 생기면 12강 24~28단계처럼 편집기에 옮기고, 테스트 실행 뒤 `실행기록` 탭에 한 줄이 생기는지 봅니다.

## 손에 남길 것과 완료 확인

**실패 대응표 1장(다섯 줄 × 다섯 칸) · 실행기록 탭 · 수동 절차 3줄 · 인계 메모 양식**

- [ ] 실패 모양 다섯 가지 모두에 기록할 곳 · 되돌리는 법 · 다른 길을 적었다
- [ ] 트리거 실패 알림을 켜고 빈도를 정했다
- [ ] 실행 기록을 편집기에만 두지 않고 시트에 따로 남긴다
- [ ] "성공"은 저장·발송이 끝난 뒤에만 기록되는 것을 확인했다
- [ ] 실패와 건너뜀을 다른 값으로 기록한다
- [ ] 버전 기록으로 되돌리기를 실제로 한 번 해 보았다
- [ ] 자동화마다 수동 절차를 세 줄로 적었다
- [ ] 인계 메모 양식을 만들었다
- [ ] "멈췄다"고 말하기 전에 확인할 것을 정했다

실패 대응표는 한 번 쓰고 끝나는 문서가 아닙니다. 실제로 실패가 일어날 때마다 한 줄씩 늘어납니다. 20강에서 이 표의 줄 수를 셉니다.

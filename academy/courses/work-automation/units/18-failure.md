# 18강. 자동화가 실패할 때 — 기록하고, 되돌리고, 다른 길로

유정근 · 마이웨이 아카데미 | C3 업무 자동화
척추: 12블럭 B12

## 오늘의 목표

내 자동화가 실패하는 모양을 미리 다섯 가지로 나눠 보고, 실패마다 **기록할 곳 · 되돌리는 법 · 다른 길** 세 칸을 채운 "실패 대응표" 한 장과, 다른 사람(또는 다른 AI)에게 일을 넘길 때 쓰는 인계 메모 양식을 만듭니다.

## 먼저 이해하기

자동화는 반드시 실패합니다. 문제는 실패 그 자체가 아니라, 실패가 **조용히** 일어나는 것입니다. 사람이 하던 일은 실패하면 사람이 압니다. 자동화의 실패는 아무도 모르는 채로 며칠씩 이어질 수 있습니다. 그래서 실패 대응은 세 동사로 정리됩니다.

- **기록한다.** 실패는 크게 드러나야 합니다. "성공"은 정말 성공한 뒤에만 적습니다.
- **되돌린다.** 바꾸기 전에 원본을 남기고, 되돌리는 길을 미리 한 번 걸어 봅니다.
- **다른 길로 간다.** 한 경로가 막혔을 때 쓸 대체 경로를 정해 둡니다. 수동 절차도 훌륭한 대체 경로입니다.

비유하자면 산행의 하산 계획입니다. 노련한 등산가는 정상에 가는 길보다 내려오는 길을 먼저 확인합니다. 몇 시까지 정상에 닿지 못하면 돌아선다는 시각, 날씨가 나빠지면 쓸 우회로, 산에 오른다고 알려 둔 사람. 이것이 각각 정지선, 다른 길, 기록입니다.

## 강사의 시스템에서

강사의 워크스페이스에는 실패 기록이 성공 기록만큼 많습니다. 여기서는 모양이 서로 다른 다섯 가지를 봅니다.

**① 권한 창 앞에서 멈춘 무인 실행.** 사람이 자리를 비운 사이 AI에게 작업을 맡겼는데, AI가 파일을 쓰기 전 권한을 묻는 창을 띄웠고 그 창에 답할 사람이 없었습니다. 결과는 아무 파일도 만들어지지 않은 채 끝난 작업이었습니다. C1에서 배운 권한 창은 사람이 곁에 있을 때는 안전장치지만, 사람이 없을 때는 정지 버튼이 됩니다. 사람 없이 돌릴 일이라면 권한 범위를 미리 좁게 정해 두거나, 사람이 확인할 수 있는 방식으로 좁은 범위부터 시험합니다. 그리고 끝났다는 보고가 아니라 <strong>결과 파일이 실제로 있는지</strong>로 확인합니다.

**② 사용 한도에 걸려 멈춘 작업.** 긴 작업 도중 AI 도구의 사용 한도가 차서 일이 멈췄고, 남은 일을 다른 AI 에이전트에게 넘겨 마쳤습니다. 이때 넘겨받는 쪽이 가장 먼저 묻는 것은 늘 같습니다. 무엇이 끝났고, 무엇이 남았고, 파일은 어디 있고, 무엇을 건드리면 안 되는가. 강사가 앓아누운 주에 세 에이전트가 일을 나눠 맡을 때도 한도에 대비한 인계 절차를 보고서의 한 절로 따로 두었습니다. 인계 메모가 있으면 한도는 사고가 아니라 교대 시간입니다.

**③ 멈췄는데 살아 있던 작업.** 중단 버튼을 눌렀는데, 뒤에서는 작업이 계속 살아 이어지고 있던 일이 있었습니다. 로컬 작업실 설명서에는 이 차이가 정확히 적혀 있습니다. "다음 작업 일시정지"는 지금 작업을 멈추지 않습니다. "이 작업 취소"는 현재 모델 응답을 받은 뒤에 결과를 버립니다. "서버 종료"는 화면 서버를 닫을 뿐, 모델 프로그램은 따로 돌고 있어서 진행 중이던 추론이 잠시 남을 수 있습니다. 교훈은 단순합니다. 멈춤 버튼을 누른 뒤에는 <strong>결과 폴더에 새 파일이 더 생기지 않는지</strong>를 확인하고 나서야 멈췄다고 말합니다.

**④ 성공으로 보인 실패.** 5강의 "처리함을 먼저 적어 통화 한 건이 조용히 증발하는 순서"와 9강의 "승인 실패를 성공으로 표시하던 결재 화면"은 같은 점검에서 함께 나온 결함입니다. 둘 다 오류 메시지 하나 없이 틀립니다. <strong>성공 기록은 성공한 뒤에, 실패는 크게.</strong>이 원칙을 뒤집는 코드는 동작해도 틀린 코드입니다.

**⑤ 멈추지 않고 끝까지 돌린 판단.** 9강에서 본 대리 결재 사고(순번이 당겨져 보류했던 건이 승인된 일)에는 뒷이야기가 있습니다. 에이전트는 잘못을 알아챘을 때 실행을 중간에 끊지 않았습니다. 승인 한 건은 초안 생성 → 파일 이동 → 목록 등록 → 캘린더 등록 순서로 진행되는데, 중간에 끊으면 파일은 옮겨졌는데 목록은 비어 있는 반쪽 상태가 남습니다. 중복 문서 한 건보다 반쪽 상태가 더 비싸다고 보고 끝까지 돌린 뒤, 결재 스레드에 "롤백"이라고 답하면 작동하는 공식 되돌리기 경로를 보고서에 적었습니다. **되돌리기는 도중에 끊는 것이 아니라, 끝난 뒤 정해진 길로 돌아가는 것입니다.**

11강의 캘린더 사고는 되돌리기의 순서를 그대로 보여 줍니다. 지우기 전에 백업하고, 한 건이 아니라 공통 함수를 고치고, 같은 조건으로 사고를 재현해 가드가 막는지 확인했습니다.

강사가 가장 경계하는 실패는 따로 있습니다. "됐다고 보고했는데 실제로는 안 된" 경우입니다. 클라우드 에이전트 기록에는 배포 중 실수를 숨기지 않고 적은 이유가 이렇게 남아 있습니다. "이 프로젝트가 '됐다고 보고했는데 안 되는' 패턴으로 이미 한 번 막혔기 때문이다."

## 가상 예시로 직접 해 보기

아래 인물·자료·기관은 학습용 가상 설정입니다.

1. 윤하람 씨는 12강의 "설문지 → 시트 → 알림"과 16강의 "주간 요약 저장" 자동화를 놓고 실패 대응표를 만듭니다. 칸은 실패 모양 / 어떻게 알게 되나 / 기록할 곳 / 되돌리는 법 / 다른 길입니다.
2. 실패 모양을 다섯 줄 적습니다: 권한·인증에서 멈춤, 한도에서 멈춤, 멈췄는데 계속 돎, 성공으로 보인 실패, 반쯤 하다 멈춤.
3. **어떻게 알게 되나.** 앱스 스크립트는 트리거가 실패하면 실패 요약을 메일로 보내 줍니다. 트리거가 켜져 있는 동안에는 이 알림의 빈도를 조정할 수 있고, 알림을 아예 끄려면 트리거를 끄거나 지워야 합니다. 하람 씨는 트리거를 만들 때 알림 빈도 선택지를 화면에서 확인하고 가장 자주 받는 쪽을 고르기로 합니다.
4. **기록할 곳.** 편집기의 실행 기록은 개발 중 확인용이라 오래 남지 않는다고 공식 문서가 밝히고 있습니다. 그래서 하람 씨는 `실행기록` 시트를 따로 만들고 칸을 정합니다: 시각 / 자동화 이름 / 결과(성공·실패·건너뜀) / 이유. "건너뜀"은 실패가 아니라는 점을 칸 설명에 적습니다.
5. 코드의 순서를 확인합니다. "성공" 줄은 저장·발송이 끝난 다음 줄에만 있어야 합니다. 아래 두 번째 요청문으로 AI에게 점검을 맡깁니다.
6. **되돌리는 법.** 구글 문서·시트는 오른쪽 위 버전 기록에서 이전 버전을 고르고 "이 버전 복원하기"를 누릅니다. 드라이브 휴지통의 파일은 30일이 지나면 영구 삭제되므로 그 안에 복원합니다. 구글 문서가 아닌 일반 파일의 이전 버전도 30일이 지났거나 100개를 넘으면 지워질 수 있어, 남겨야 할 버전은 "영구 보관"을 누릅니다.
7. 되돌리기를 **한 번 실제로 해 봅니다.** 시험용 시트의 값을 바꾼 뒤 버전 기록으로 되돌려 봅니다. 한 번도 걸어 보지 않은 하산로는 하산로가 아닙니다.
8. **다른 길.** 자동화마다 수동 절차를 세 줄로 씁니다. 예) "요약이 안 오면: ① 신청 시트를 연다 ② 필터로 이번 주만 본다 ③ 과정별 개수를 세어 메모한다".
9. **반쯤 하다 멈춤** 칸에는 "도중에 끊지 않는다, 끝난 뒤 되돌린다"를 적고, 작업이 여러 걸음이면 걸음마다 결과가 어디에 남는지 나열합니다.
10. <strong>인계 메모 양식</strong>을 만듭니다. 칸: 목표 / 끝난 것 / 남은 것 / 파일 위치(폴더 이름만) / 건드리면 안 되는 것 / 마지막으로 확인한 결과와 시각. 사용 한도로 AI를 바꿔야 할 때 이 양식을 채워 새 대화에 붙여 넣습니다.
11. 대응표 맨 아래에 "멈췄다고 말하기 전에 확인할 것"을 한 줄 씁니다. 하람 씨의 답: "결과 폴더에 5분 동안 새 파일이 생기지 않는다".

## AI에게 건네는 말

> 내 자동화 설계서와 코드를 읽고, 실패 모양 다섯 가지(권한·인증에서 멈춤 / 한도에서 멈춤 / 멈췄는데 계속 돎 / 성공으로 보인 실패 / 반쯤 하다 멈춤) 각각이 이 자동화에서 어떻게 일어날 수 있는지 한 줄씩 적어 줘. 일어날 수 없는 것은 왜 없는지도 적어 줘. 코드는 고치지 마.

> 이 앱스 스크립트에서 "성공" 기록이나 "처리함" 표시가 실제 저장·발송보다 먼저 실행되는 곳이 있는지 찾아 줘. 오류가 났을 때 그 사실이 `실행기록` 시트에 '실패'와 이유로 남는지도 확인해 줘. 한도 때문에 건너뛴 경우는 '실패'가 아니라 '건너뜀'으로 남아야 해.

## 손에 남길 것과 완료 확인

**실패 대응표 1장(다섯 줄 × 다섯 칸) · 실행기록 시트 · 수동 절차 3줄 · 인계 메모 양식**

- [ ] 실패 모양 다섯 가지 모두에 기록할 곳 · 되돌리는 법 · 다른 길을 적었다
- [ ] 트리거 실패 알림을 켜고 빈도를 정했다
- [ ] 실행 기록을 편집기에만 두지 않고 시트에 따로 남긴다
- [ ] "성공"은 저장·발송이 끝난 뒤에만 기록되는 것을 확인했다
- [ ] 실패와 건너뜀을 다른 값으로 기록한다
- [ ] 버전 기록으로 되돌리기를 실제로 한 번 해 보았다
- [ ] 자동화마다 수동 절차를 세 줄로 적었다
- [ ] 인계 메모 양식을 만들었다
- [ ] "멈췄다"고 말하기 전에 확인할 것을 정했다

실패 대응표는 한 번 쓰고 끝나는 문서가 아닙니다. 실제로 실패가 일어날 때마다 한 줄씩 늘어납니다. 20강에서 이 표의 줄 수를 셉니다.
